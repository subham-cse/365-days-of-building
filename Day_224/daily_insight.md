# Day 224: Kotlin `@JvmInline value class` & Unboxing Overhead Traps

**Language / Domain**: Kotlin / JVM Interop & Performance

**The Core Concept / "Did You Know?"**:
Kotlin provides `@JvmInline value class` wrappers to create domain-specific type abstractions (such as `UserId(val id: Long)` or `Meters(val value: Double)`) with zero runtime heap allocation overhead. The Kotlin compiler attempts to unbox value classes directly into primitive types at runtime.

However, value classes do **not** eliminate boxing in all scenarios! If a value class is used as a generic type argument (`List<UserId>`), cast to an interface (`Comparable<UserId>`), assigned to a nullable type (`UserId?`), or passed to a function taking `Any`, the Kotlin compiler is forced to box the primitive back into a wrapper object on the JVM heap.

**The Code Snippet**:
```kotlin
@JvmInline
value class UserId(val rawId: Long) : Comparable<UserId> {
    override fun compareTo(other: UserId): Int = rawId.compareTo(other.rawId)
}

@JvmInline
value class Currency(val amount: Double)

class ValueClassDemo {

    // Zero Allocation: Compiled directly to primitive JVM signature: processUser(long rawId)
    fun processUserDirect(id: UserId) {
        println("Processing primitive user ID: ${id.rawId}")
    }

    // UNBOXING TRAP 1: Nullable value classes force JVM Object Boxing!
    fun processNullableUser(id: UserId?) {
        // Compiled to JVM signature: processNullableUser(UserId id) -> Heap Allocation!
        if (id != null) {
            println("Nullable ID: ${id.rawId}")
        }
    }

    // UNBOXING TRAP 2: Generics force JVM Object Boxing!
    fun processUserList(users: List<UserId>) {
        // Compiled to List<Object> containing boxed UserId instances on heap
        for (user in users) {
            println("Generic user: ${user.rawId}")
        }
    }

    // UNBOXING TRAP 3: Interface casting forces JVM Object Boxing!
    fun compareValues(a: Comparable<UserId>, b: UserId) {
        // Passing 'a' as interface boxes the value class!
        a.compareTo(b)
    }
}

fun main() {
    val id = UserId(42L)
    val demo = ValueClassDemo()

    demo.processUserDirect(id)        // Direct primitive long pass (No Heap allocation)
    demo.processNullableUser(id)      // Boxes UserId object on JVM heap!
    demo.processUserList(listOf(id))  // Boxes UserId object inside List container!
}
```

**Under the Hood / Why It Happens**:
Inspect the decompiled Java bytecode generated by Kotlinc:
1. `fun processUserDirect(id: UserId)` generates:
   ```java
   public final void processUserDirect_impl-51K00(long id) { ... }
   ```
   The compiler mangles the function name to prevent signature collisions and passes raw `long id` on the JVM execution stack.

2. `fun processNullableUser(id: UserId?)` generates:
   ```java
   public final void processNullableUser(UserId id) { ... }
   ```
   Because JVM primitive types (`long`, `double`, `int`) cannot hold Java `null` references, Kotlin must instantiate a heap wrapper object `UserId` when nullable type `UserId?` is declared.

3. Generic collections `List<T>` on the JVM erase to `java.util.List<Object>`. Since primitives cannot populate `List<Object>`, Kotlin boxes the value class.

**Key Takeaway / Safe Pattern**:
- Use `@JvmInline value class` for domain-driven primitives (`AccountNumber`, `Seconds`) when passing values directly to non-generic functions or storing them inside unboxed primitive arrays (`LongArray`).
- Avoid using nullable versions of value classes (`UserId?`) on high-throughput hot paths. Use sentinel primitive constants (e.g., `UserId(-1L)`) if zero allocation is strictly required.
- Be cautious when storing value classes in generic collections like `List<T>` or `Map<K, V>`, as object boxing will occur.
